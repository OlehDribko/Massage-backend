# Транзакційні повідомлення про бронювання (Notifications)

Окремий **модуль** (`services/booking/src/notifications`) надсилає листи про створення, перенесення й скасування запису клієнту й студії через замінний адаптер Brevo. **Виконується в процесі API** — свідомий компроміс поточного етапу (погоджено 2026-11-01): без окремого worker, черг і опитування БД.

**Стан.** Реалізовано й перевірено з PostgreSQL і фейковим поштовим провайдером. Реальні листи не надсилалися. Міграцію `20261031120000_booking_notifications` не застосовано, на staging надсилання не ввімкнено (розділ 10).

## 1. Архітектура

```
HTTP-запит ─> транзакція календаря: Booking + OutboxEvent (атомарно) ─> відповідь клієнту
                                   └─ після транзакції: wake() ─┐   (відповідь не чекає листа)
                                                                 v
                              dispatcher (у процесі API) ─> прохід: план → надсилання → результат
                                                                 │                   │
                                         NotificationEvent / NotificationDelivery    EmailProvider (Brevo)
```

- **У процесі API, але окремим модулем.** Код Notifications не імпортує модулі бронювань, каталогу чи профілів. API передає йому лише сигнал `wake()` (`bootstrap.ts`, `NotificationsRuntime`). Читання статусів для API — `status.ts`.
- **Коли виконується прохід** (`dispatcher.ts`):
  1. після кожного запису календаря бронювань — успішного чи ні (результат невдалого COMMIT може бути невідомим, а прохід дешевий);
  2. один раз під час запуску процесу — **відновлення** (розділ 5);
  3. за **одним таймером** — лише для конкретної незавершеної роботи: час наступної повторної спроби або закінчення чужої оренди. Таймер обчислюється з БД після кожного проходу.
- **Без роботи — жодних звернень до БД.** Циклу опитування немає; таймер не ставиться; пул закриває простійні з'єднання через 30 с, тож Neon може заснути.
- **Межі доступу:**
  - модуль **лише читає** `OutboxEvent` і пише тільки у власні таблиці `NotificationEvent` і `NotificationDelivery`;
  - таблиць каталогу, профілів і бронювань він не торкається: усі дані про запис бере з події;
  - доменних подій не створює: їх пише лише модуль бронювань у транзакції календаря;
  - межу перевіряє тест `test/notifications-config.test.ts`, «component boundaries».
- **Brevo — замінний адаптер** (`EmailProvider`, `brevo-provider.ts`). Під час виклику Brevo немає ні відкритої транзакції, ні виділеного з'єднання БД.

## 2. Контракт подій (споживач)

Продюсер — `src/modules/bookings/booking.events.ts`; споживач — `src/notifications/event-contract.ts`, `schemaVersion` = 1.

| Поле | Використання |
|---|---|
| `type` | `booking.created`, `booking.rescheduled`, `booking.cancelled` |
| `position` | Порядок фіксації. Події пише лише транзакція календаря під глобальним advisory lock, тож наступна транзакція бере `position` лише після фіксації попередньої (`docs/booking.md`, розділ 4) |
| `payload.client.email` | Адреса клієнта (стан на момент події) |
| `payload.startsAt/endsAt/timeZone`, `service`, `previous`, `cancellation` | Зміст листа |

Подія, яку неможливо використати, отримує **видимий** стан `NotificationEvent.status = invalid` і безпечний `reasonCode`. Можливі коди: `unsupported_aggregate`, `unsupported_event_type`, `unsupported_schema_version`, `invalid_payload`, `inconsistent_payload`. Помилка пишеться в лог з кодом. Мовчки нічого не відкидається.

Поле `OutboxEvent.publishedAt` **не використовується** (завжди `null`): одна подія має кількох одержувачів, і одне поле не може точно описати результат. Колонку тимчасово залишено для сумісності (розділ 12). Прогрес доставки описують:
- `NotificationEvent.processedAt` — подію розглянуто: доставки записано або подію визнано невалідною. **Це не означає, що листи надіслано.**
- Стан кожного листа — окремий рядок `NotificationDelivery`.

## 3. Листи

| Подія | Клієнт | Студія |
|---|---|---|
| `booking.created` | «Votre rendez-vous est confirmé»: дата й час (Europe/Paris), послуга, тривалість, ціна в EUR, оплата на місці | «Nouveau rendez-vous»: те саме + ім'я, email, телефон клієнта |
| `booking.rescheduled` | «Votre rendez-vous a été déplacé»: старий і новий час, повна інформація про запис | «Rendez-vous déplacé»: старий і новий час + клієнт |
| `booking.cancelled` | «Votre rendez-vous a été annulé»: хто скасував (ви / студія), причина, якщо є | «Rendez-vous annulé»: хто скасував, причина + клієнт |

- **Мова й формати.** Французька; дати форматуються через `Intl` у Europe/Paris з урахуванням DST; ціна — з цілих центів (`65,00 €`).
- **Самодостатність.** Кожен лист клієнту містить повну інформацію про запис, навіть якщо попередній лист пропущено.
- **Що бачить клієнт.** Жодних службових ID (бронювання, профілю, події) і внутрішніх даних студії.
- **Безпека змісту.** Динамічні дані в HTML екрануються; є plain-text версія; тема однорядкова, керівні символи прибрано.
- **Посилань немає:** маршрут сторінки бронювання у frontend ще не погоджено. Лист повний і без посилання. Додавати посилання — лише після появи задокументованого маршруту.
- **Транзакційний характер.** Листи не залежать від маркетингової підписки. Маркетинг, нагадування й `.ics` не реалізовано.

**Одержувачі** фіксуються при першому формуванні події:
- клієнт — адреса з події;
- студія — одна адреса `NOTIFICATION_STUDIO_EMAIL` на той момент. Пошуку профілів `admin` немає.

Зміна адреси студії не додає доставок для вже сформованих подій.

## 4. Облік доставок (`NotificationDelivery`)

Один рядок — один лист одному одержувачу для однієї події; унікальність `(eventId, recipientRole)`.

| Поле | Зміст |
|---|---|
| `id` | UUID доставки, **він же ключ ідемпотентності Brevo** (однаковий у всіх спробах) |
| `status` | `pending` → `in_progress` → `accepted` / `failed` / `skipped` |
| `attempts`, `nextAttemptAt` | Кількість спроб і час наступної |
| `leaseOwner`, `leaseToken`, `leaseExpiresAt` | Оренда: хто й до коли обробляє; `leaseToken` новий на кожне захоплення |
| `lastErrorCode` | Код останньої помилки (фіксований, без тексту провайдера) |
| `resultCode` | Фінальний результат (таблиця нижче) |
| `providerMessageId`, `acceptedAt` | ID повідомлення Brevo і час прийняття |

| Стан | `resultCode` | Значення |
|---|---|---|
| `accepted` | `accepted` | **Прийнято Brevo**, а не «доставлено в скриньку». Webhook-статусів доставки в цьому етапі немає |
| `accepted` | `accepted_duplicate` | Brevo відповів `duplicate_parameter`: цей ключ уже прийнято раніше (спроба, що впала після прийняття). `providerMessageId` невідомий |
| `failed` | `recipient_missing` / `recipient_invalid` | У події немає або некоректна адреса клієнта |
| `failed` | `provider_rejected` | Brevo відхилив лист (4xx, крім ідемпотентності й конфігурації); повтор не допоможе |
| `failed` | `attempts_exhausted` | Тимчасові помилки до межі спроб; `lastErrorCode` — остання причина |
| `failed` | `provider_auth` / `provider_forbidden` / `provider_account` | Помилка конфігурації Brevo (ключ, права, рахунок): одна спроба, без повторів |
| `failed` | `interrupted` | Остання дозволена спроба була захоплена процесом, який зупинився без результату; невідомо, чи отримав її Brevo |
| `failed` | коди з розділу 2 | Невалідні дані події на момент надсилання |
| `skipped` | `recipient_not_allowed` | Не production, адреси немає в allowlist |
| `skipped` | `superseded` / `session_already_started` | Застарілий лист клієнту (розділ 6) |

**Обмеження БД:**
- поля оренди заповнені лише в `in_progress`;
- фінальні стани мають `completedAt` і `resultCode`;
- `accepted` завжди має `acceptedAt`.

## 5. Гарантії, повтори й відновлення

### Що гарантує БД, а що — ні
- **Атомарність.** Бронювання й подія записуються в одній транзакції. Помилка надсилання не скасовує й не змінює бронювання.
- **Без дубля завдання:** унікальні `NotificationEvent.eventId` і `(eventId, recipientRole)` не дають створити другу доставку тому самому одержувачу для тієї самої події.
- **Lease і fencing захищають стан БД, а не зовнішній ефект.** Лист може бути надіслано вдруге, якщо:
  1. Brevo прийняв лист, а процес зупинився до запису результату;
  2. запис результату затримався довше за оренду (60 с) і доставку взяв інший процес;
  3. Brevo фактично прийняв лист, але відповів тайм-аутом або 5xx.
  
  Повтор завжди йде з **тим самим ключем ідемпотентності** (`delivery.id`), тож у межах вікна Brevo (30 хв за документацією) другого листа немає (`accepted_duplicate`). Усі три спроби вкладаються у це вікно (розділ «Повтори»). **Залишковий ризик:** повтор після закінчення вікна (наприклад, процес зупинився після прийняття листа і перезапустився пізніше ніж через 30 хв) дає другий лист. Фактичну поведінку Brevo ще треба перевірити на реальному акаунті. Тест: «residual risk, documented».

### Ідемпотентність Brevo (перевірено за документацією 2026-10-31)
- **Ключ:** `POST /v3/smtp/email` приймає ключ ідемпотентності в тілі запиту, `headers.idempotencyKey` (UUID).
- **Вікно:** у межах TTL повторний запит з тим самим ключем не обробляється й повертає помилку `duplicate_parameter`; лист повторно не надсилається.
- **TTL:** поточна документація — **30 хвилин**; changelog 2021 року вказував 15 хвилин. Розраховуємо на 30, фактичну поведінку треба перевірити на реальному Brevo.
- Джерела: [Idempotency in batch emails](https://developers.brevo.com/docs/heterogenous-versions-batch-emails), [changelog 2021-11-10](https://developers.brevo.com/changelog/2021/11/10).

### Оренда
- **Коротке захоплення.** `SELECT … FOR UPDATE SKIP LOCKED` + `UPDATE` ставить `in_progress`, власника, новий `leaseToken`, строк оренди (60 с) і `attempts + 1`. Виклик Brevo — **поза транзакцією**.
- **Тайм-аут запиту** — 20 с; вбудовані повтори SDK Brevo вимкнено (`maxRetries: 0`), тож повторів поверх наших немає.
- **Fencing.** Результат записується лише за `status = in_progress AND leaseToken = <свій>`; запізнілий запис відкидається з попередженням у лозі.
- **Кілька процесів API** (наприклад, під час розгортання) безпечні: `SKIP LOCKED` і оренда не дають двом процесам узяти одну доставку.
- **Завершення процесу** (`SIGTERM`): нова робота не захоплюється; лист, що надсилається, завершується в межах `SHUTDOWN_TIMEOUT_MS`; захоплені, але не розпочаті доставки повертаються в `pending` без витрати спроби. Якщо дедлайн зупинки сплив під час виклику Brevo, доставка лишається `in_progress` і продовжується після наступного запуску з тим самим ключем.

### Порядок
Ланцюжок — (бронювання, одержувач). Доставка доступна, лише коли в її ланцюжку немає ранішої (`eventPosition` менший) незавершеної доставки. Наслідки:
- листи одному одержувачу про одне бронювання йдуть у порядку подій, **разом із повторними спробами**;
- ланцюжки клієнта й студії незалежні: збій листа студії не затримує листів клієнту, і навпаки.

### Класифікація помилок і повтори (погоджено 2026-11-01)
**Максимум три спроби для кожного одержувача:** початкова й дві повторні. Спроби рахуються в БД (`attempts`), тож межа діє й після перезапуску.

| Результат | Дія |
|---|---|
| 2xx | `accepted` |
| 400 `duplicate_parameter` | `accepted` (`accepted_duplicate`) |
| 429, 5xx, 408, тайм-аут, мережа | Повтор: через **1 хв**, потім через **5 хв**, кожна пауза + до 20 % випадкового jitter; не раніше `Retry-After`, але не довше **10 хв**. Після 3-ї спроби — `failed` (`attempts_exhausted`) |
| Інші 4xx | `failed` (`provider_rejected`) одразу, без повторів |
| 401, 403, 402 (ключ, права, рахунок) | `failed` з кодом `provider_auth` / `provider_forbidden` / `provider_account` **одразу**, без повторів: повтор за хвилини не допоможе. Помилка в лозі; виправлення — зміна конфігурації |
| Некоректна адреса | Перевіряється до надсилання → `failed` (`recipient_invalid`) |

**Чому `Retry-After` обмежено 10 хв:** найпізніший початок 3-ї спроби — ≈ 20.7 хв після 1-ї (2 × (10 хв + 20 с тайм-ауту)), тобто в межах 30-хвилинного вікна ідемпотентності Brevo. Це перевіряє `tuningErrors` у `config.ts` і тест конфігурації. Якщо Brevo просить чекати довше, спроба все одно відбудеться через 10 хв і може знову отримати 429: це одна з трьох спроб.

**Після вичерпання спроб** — `failed`, без нескінченних автоматичних повторів і без ручної функції повторного надсилання в API.

### Відновлення (свідомі обмеження)
Під час запуску процес робить один прохід: планує незаплановані події, бере `pending` з настанням часу та `in_progress` з минулою орендою (з урахуванням межі спроб), а для решти ставить таймер. Чинна оренда іншого процесу поважається: таймер стоїть на час її закінчення.

**Гарантованого негайного відновлення при всіх аваріях немає.** Завдання чекає наступного пробудження (будь-якого запису бронювання в цьому процесі) або **наступного запуску**, якщо:
1. процес зупинився (падіння, `SIGKILL`, перезапуск ECS) між фіксацією бронювання й своїм проходом, а **новий процес стартував раніше** (розгортання з перекриттям задач: стартовий прохід нової задачі вже відбувся);
2. процес зупинився під час спроби, а інші процеси не мали таймера на закінчення цієї оренди;
3. COMMIT бронювання завершився з невідомим результатом, а сервер зафіксував транзакцію вже після проходу;
4. БД була недоступна під час проходу: після 3 повторів проходу (30 с, 2 хв, 10 хв) диспетчер чекає наступного пробудження;
5. сервіс на паузі (`desired_count = 0`) — до запуску;
6. стан змінено вручну (`UPDATE` у БД) — процес про це не знає; потрібен перезапуск API або наступний запис бронювання;
7. робота стала доступною, але жоден прохід не зміг її взяти кілька разів поспіль (захоплено іншим процесом) — диспетчер пише попередження й чекає.

Прихованого резервного опитування немає: це прийнятий компроміс. **Прострочена обробка не виглядає вічно як «надсилаємо»:** API показує `interrupted`, щойно оренда минула або завдання прострочене більш ніж на 15 хв (розділ 11); після перезапуску остання перервана спроба, якщо спроби вичерпано, стає `failed` (`interrupted`).

## 6. Застарілі листи (погоджено 2026-10-31)

Стосується лише **листів клієнту** про підтвердження й перенесення, ще не прийнятих Brevo:

| Ситуація | Клієнт | Студія |
|---|---|---|
| Підтвердження ще не надіслано, а в outbox уже є новіша подія цього запису | `skipped` (`superseded`) | надіслати |
| Кілька перенесень до надсилання | надсилається лише актуальне; старіші `superseded` | кожне по порядку |
| Скасування | **завжди** | завжди |
| Накопичені після паузи: сеанс уже почався | `skipped` (`session_already_started`) | надіслати |
| Накопичені після паузи: сеанс ще попереду | надіслати | надіслати |

- **Уже прийняті листи** не змінюються й не повторюються.
- **Самодостатність.** Актуальний лист містить повну інформацію про запис, навіть якщо попереднє підтвердження пропущено.
- **Немає вікового порогу** на кшталт «старше 24 годин».
- **Вузьке вікно гонки.** Якщо новіша подія з'явилася між перевіркою й надсиланням, клієнт отримає обидва листи.

## 7. Конфігурація

Змінні читає API (`loadConfig` → `config.notifications`). Помилка конфігурації при `ENABLE_BOOKING_NOTIFICATIONS=true` зупиняє запуск API з переліком змінних, без значень.

| Змінна | Обов'язково | Опис |
|---|---|---|
| `ENABLE_BOOKING_NOTIFICATIONS` | ні (`false`) | Без `true` диспетчер не створюється: подій ніхто не обробляє (вони лишаються в outbox), API не звертається до Brevo, у переглядах бронювань `notification: null`. Не залежить від `ENABLE_MARKETING_SUBSCRIPTION` |
| `NOTIFICATIONS_ENVIRONMENT` | так, при увімкненні | `production`, `staging` або `development` |
| `NOTIFICATION_RECIPIENT_ALLOWLIST` | поза production — так | Список дозволених тестових адрес через кому. Без нього API на staging/development **не стартує**. У production заборонено. Інші одержувачі отримують видимий `skipped` (`recipient_not_allowed`), а не тиху підміну адреси |
| `NOTIFICATION_STUDIO_EMAIL` | так | Адреса студії-одержувача |
| `BREVO_API_KEY` (**секрет**), `EMAIL_FROM_NAME`, `EMAIL_FROM_EMAIL` | так | Ті самі імена, що й для маркетингу; прапорці незалежні |

БД — та сама, що й API (`DATABASE_URL`). Роль `booking_app` уже має DML на таблиці Notifications: раннер міграцій видає права на всі таблиці migrator.

Параметри роботи задано в коді (`DEFAULT_TUNING` у `config.ts`): 3 спроби, повтори 1 і 5 хв (+20 % jitter), `Retry-After` до 10 хв, оренда 60 с, тайм-аут 20 с, пакет 10, планування по 50 подій.

**Логи:** ID доставки й події, тип, роль одержувача, стан, код. Без адрес, тем, тіл листів, ключів і сирих відповідей Brevo.

## 11. Статус повідомлень в API

Статус бронювання (`status`) і статус повідомлення — різні поля. Статуси читаються під час відкриття чи оновлення сторінки (`GET`); постійного опитування чи realtime-каналу немає.

**Клієнт** (`GET /api/bookings`, `GET /api/bookings/:id` і відповіді на створення, перенесення, скасування) — лише власний лист про **останню** зміну запису:

```json
"notification": { "event": "created", "status": "failed", "reason": "not_sent" }
```

`notification: null` — надсилання вимкнено на цьому сервері.

| `status` | Значення | Приклад тексту для клієнта |
|---|---|---|
| `pending` | Очікує першої спроби або повтору (`reason: "retry_scheduled"`) | «Лист надсилається» |
| `sending` | Спроба триває зараз | «Лист надсилається» |
| `accepted` | **Прийнято поштовим провайдером** для надсилання. Це **не** «доставлено в скриньку» | «Лист із деталями надіслано» |
| `failed` | Не вдалося надіслати (`not_sent`) або немає коректної адреси (`no_valid_address`) | «Бронювання підтверджено, але лист не вдалося надіслати. Деталі запису доступні у вашому кабінеті» |
| `skipped` | Не надсилався за погодженим правилом: `superseded` (є новіший лист), `session_already_started`, `test_environment` (тестове середовище) | — |
| `interrupted` | Обробку перервано, повідомлення продовжиться після відновлення сервісу | «Лист затримується. Деталі запису доступні у вашому кабінеті» |

**Адміністратор** (`GET /api/admin/bookings?date=…`, `GET /api/admin/bookings/:id`, відповідь на скасування) — результати обох одержувачів для кожної зміни запису, від найстарішої:

```json
"notifications": [
  { "event": "created", "occurredAt": "…",
    "client": { "status": "accepted", "reason": null, "attempts": 1, "lastAttemptAt": "…", "acceptedAt": "…" },
    "studio": { "status": "failed", "reason": "provider_configuration", "attempts": 1, "lastAttemptAt": "…", "acceptedAt": null } }
]
```

Причини для адміністратора — фіксовані коди: `retry_scheduled`, `superseded`, `session_already_started`, `test_environment`, `no_valid_address`, `temporary_errors`, `provider_rejected`, `provider_configuration`, `invalid_event`, `processing_interrupted`, `processing_delayed`, `other`. Сирих помилок Brevo, адрес одержувачів, ключів і ID провайдера API не віддає. Функції повторного надсилання немає.

## 12. Сумісність міграції з іншими версіями API

Міграція `20261031120000_booking_notifications` лише **додає** таблиці й enum-и, а `OutboxEvent` не змінює. Колонку `publishedAt` у ній свідомо **не видалено**.

**Чому не видалено.** Перевірено експериментом на PostgreSQL. Prisma Client версії з бронюваннями (`develop` до цього PR, `399f177`) при записі події повертає всі поля моделі, зокрема `publishedAt`. Якщо колонки немає, кожен запис падає з помилкою «The column `OutboxEvent.publishedAt` does not exist». Подія пишеться в одній транзакції з бронюванням, тож стара версія не змогла б створити, перенести чи скасувати жоден запис. З колонкою той самий клієнт працює.

| Версія API на новій схемі | Результат |
|---|---|
| Розгорнута зараз на staging (`c5b009f`, етап Firebase; ревізія `:4`) | Сумісна: таблиць бронювань і outbox не використовує |
| Попередня версія з бронюваннями (`399f177`) — під час rollout, поки стара задача ще працює | Сумісна: колонка лишилася, нові таблиці їй не заважають |
| Відкат після застосування міграції — на `399f177` або `c5b009f` | Сумісний: схема для них лише розширена; міграцію не потрібно відкочувати |
| Нова версія (цей PR) | Колонку не читає й не пише; Prisma Client повертає її як `null` |

**Остаточне видалення** `publishedAt` (і індексу `OutboxEvent_publishedAt_position_idx`) — окремою пізнішою міграцією в релізі, коли жодна старіша версія вже не зможе запуститися: не раніше, ніж поточна версія стане базовою для відкату.
