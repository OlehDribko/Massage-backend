# Архітектура: модульний моноліт

**Рішення (погоджено власником 2026-10-31).** Для поточного масштабу бекенд — **модульний моноліт**:
- один основний застосунок зі спільним деплоєм його модулів;
- одна PostgreSQL БД застосунку (Neon);
- модулі з чіткою відповідальністю, які взаємодіють звичайними викликами функцій.

Це рішення **замінює** мікросервісний напрям із [ARCHITECTURE_READINESS.md](../ARCHITECTURE_READINESS.md): окремі сервіси, SQS і `notifications-worker`, `packages/*`, незалежні деплої. Переписування чи перейменування не потрібне: код уже має таку форму.

## Що запускається

| Одиниця | Що це | Мікросервіс? |
|---|---|---|
| `services/booking` → образ `booking-api`, ECS-сервіс `booking-api` | Весь HTTP-застосунок з усіма модулями, зокрема надсиланням листів | Ні — це і є моноліт. Назва папки `services/` — npm workspace, а не ознака мікросервісів |
| Образ `booking-migrate`, одноразова задача ECS | Міграції Prisma і права ролі `booking_app` | Ні — допоміжний інструмент |
| `dist/admin/assign-role.js` (той самий образ API) | Призначення ролі власником, одноразова команда | Ні |
| CI, ECR publish, Staging deploy | GitHub Actions | Ні |

**Зовнішні провайдери** лишаються зовнішніми: Firebase Authentication (вхід), Neon (PostgreSQL), Brevo (пошта).

## Модулі

Код — `services/booking/src`. Структура не переставляється заради форми.

| Модуль | Відповідальність | Таблиці (власник) | Маршрути |
|---|---|---|---|
| `modules/auth`, `integrations/firebase` | Перевірка Firebase ID token (з перевіркою відкликання), тип ідентичності | — | — |
| `modules/profiles`, `admin/` | Профілі, ролі, синхронізація з токеном; призначення ролі — консольна команда | `UserProfile` | `/api/me` |
| `modules/access` | Політики й guards (`requireProfile`, `requireBookingClient`, `requireAdmin`) | — | — |
| `modules/marketing`, `modules/email` | Маркетингова підписка з подвійним підтвердженням; маркетингові листи Brevo і токени дій | `MarketingSubscription` | `/api/marketing`, частина `/api/me/sync` |
| `modules/catalog` | Фіксований каталог послуг, лише читання; змінюється міграціями даних | `Service` | `/api/services` |
| `modules/schedule` | Тижневий графік, винятки, доступність, **транзакція календаря** (advisory lock) | `WeeklyScheduleInterval`, `ScheduleException*` | `/api/services/:id/availability`, `/api/admin/schedule` |
| `modules/bookings` | Бронювання, перенесення, скасування, **outbox-подія в тій самій транзакції** | `Booking`, `BookingTimeChange`, `OutboxEvent` | `/api/bookings`, `/api/admin/bookings` |
| `notifications` | Листи про бронювання клієнту й студії в процесі API, облік доставок, статуси для API | `NotificationEvent`, `NotificationDelivery`; лише читає `OutboxEvent` | — (статуси віддають маршрути бронювань) |

Таблиця `User` — legacy: старі маршрути видалено, код її не використовує.

**Адміністрування** належить модулям: `/api/admin/*` монтуються з `schedule` і `bookings` за `authenticate` + `requireAdmin`. Окремого Admin-сервісу немає. Каталог послуг адмін-маршрутів не має (з 2026-11-01): він змінюється міграціями даних ([docs/booking.md](booking.md), «Каталог послуг»).

## Правила залежностей

- **Звичайні виклики.** Модулі викликають функції один одного. Внутрішніх HTTP-запитів, брокера чи шини подій немає; власного фреймворку модулів теж.
- **Таблиці змінює модуль-власник.** Інші модулі звертаються через його функції. Виняток — транзакція календаря: бронювання читають каталог і графік у ній, бо перевірка доступності й запис мають бути атомарними.
- **Спільна транзакція — за потребою функції.** Графік і бронювання виконуються під одним advisory lock (`schedule/calendar-transaction.ts`); міграції даних каталогу беруть той самий lock у явній транзакції. Подія outbox пишеться в транзакції бронювання.
- **Notifications отримує дані лише з події** і не читає таблиць бронювань, каталогу й профілів. API передає йому сигнал `wake()` через `bootstrap.ts`. Межу перевіряє тест «component boundaries».
- **Склад застосунку — у `bootstrap.ts`.** Зовнішні клієнти (Firebase, Brevo) створюються там, а не під час імпорту.

### Залежність schedule → catalog (перевірено 2026-11-01)

Залежність одностороння: **schedule → catalog**. `schedule/availability.routes.ts` імпортує `serviceIdFrom` і тип `CatalogService`: доступні години рахуються для конкретної послуги, а її тривалість дає каталог. Після прибирання адмінки каталогу catalog нічого не імпортує з schedule (раніше — лише тип `CalendarTransaction` для архівування й видалення під блокуванням). Файл транзакції календаря лишається в `schedule`.

## Notifications у моноліті

Модуль у процесі API — [docs/notifications.md](notifications.md):
- бронювання й подія зберігаються атомарно; помилка листа не скасовує бронювання;
- до 3 спроб на одержувача; стан і спроби в БД; відновлення незавершеної роботи під час запуску;
- без роботи немає ні таймерів, ні звернень до БД;
- клієнт бачить стан свого листа, адміністратор — обох одержувачів.

Outbox, облік доставок, ідемпотентність і блокування лишаються. Їх потребує функція, а не мікросервіси:
- outbox дає атомарність бронювання й події та відновлення після зупинки;
- облік доставок — ліміт спроб і статуси;
- ідемпотентність — захист від повторних запитів і повторних надсилань;
- блокування — захист від перетину бронювань.

**Lease і fencing захищають стан у БД, а не гарантують відсутність повторного листа.** Прийнятий залишковий ризик — повтор після 30-хвилинного вікна ідемпотентності Brevo (перезапуск, пауза, тривала недоступність БД). Обмеження аварійного відновлення перелічені в [docs/notifications.md](notifications.md), розділ 5.

## Що свідомо не робимо зараз

Без конкретної потреби та окремого погодження не додаємо:
- Kafka, Redis/BullMQ, SQS, Lambda-споживачів, CDC;
- окремий постійний worker чи окремий ECS-сервіс для модуля;
- окремі ECR-репозиторії й деплої на модуль, `packages/*`, окрему схему БД на модуль;
- внутрішню шину подій.

Коли переглядати: з'явиться незалежний споживач подій поза застосунком, вимога повторно читати історію подій, або навантаження надсилання почне помітно впливати на API.

**Фонова активність** (регулярні виклики платних ресурсів, постійні процеси, повтори, механізми, що не дають ресурсам засинати) описується в PR — правило в [AGENTS.md](../AGENTS.md).
