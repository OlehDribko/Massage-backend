# Заявки на подарункові сертифікати (cartes cadeaux)

Зареєстрований клієнт подає заявку на сертифікат, а студія опрацьовує її вручну: зв'язується з клієнтом, домовляється про оплату й передає сертифікат. Система лише зберігає заявку, одразу повідомляє адміністратора листом і веде статус з історією.

**Поза межами системи:** онлайн-оплата, генерація кодів сертифікатів, облік їх використання, WhatsApp-інтеграція, листи клієнту, листи про зміну статусу, frontend.

**Стан.** Реалізовано в `develop` (PR про заявки) і перевірено з PostgreSQL і фейковим поштовим провайдером. Міграцію `20261112120000_gift_card_requests` на Neon не застосовано, на staging не розгорнуто, реальних листів не надсилалося.

## 1. Модуль

`services/booking/src/modules/gift-cards` — окремий модуль моноліту ([architecture.md](architecture.md)):

| Файл | Зміст |
|---|---|
| `gift-card.schema.ts` | Валідація тіла, статуси, дозволені переходи |
| `gift-card.service.ts` | Створення (ідемпотентність, ліміт), список, деталі, зміна статусу |
| `gift-card.events.ts` | Подія outbox `gift_card_request.created` (продюсер) |
| `gift-card.view.ts`, `gift-card.routes.ts` | Відповіді API й маршрути |

- **Без календаря.** Заявка не займає час масажиста: модуль не бере глобальний advisory lock календаря й не залежить від правил графіка. З `schedule/zoned-time.ts` береться лише перетворення локальної дати на момент для фільтра списку.
- **Готовність профілю** — та сама функція `bookingReadiness` (`modules/access/policies.ts`), що й для бронювання. Guard `requireGiftCardClient` відповідає власним кодом `GIFT_CARD_REQUEST_NOT_READY` з тими самими `blockers`.
- **Ідемпотентність** — та сама перевірка заголовка, що й для бронювань (`shared/http/idempotency-key.ts`).
- **Лист адміністратору** — наявний модуль Notifications ([notifications.md](notifications.md), розділ 13): та сама черга доставок, Brevo, allowlist і повтори. Окремого worker, cron чи опитування БД немає.

## 2. Хто може подати заявку

Лише клієнт, готовий до бронювання. Усе перевіряє сервер на кожен запит:
- дійсний Firebase ID token (`401` без нього);
- роль `client`, не анонімна сесія;
- підтверджений email;
- заповнені ім'я й телефон.

Інакше `403 GIFT_CARD_REQUEST_NOT_READY { blockers }`. Можливі `blockers`: `anonymous_session`, `email_not_verified`, `name_missing`, `phone_missing`, `not_a_client`. Додатковий `phone_invalid` з'являється, якщо збережений телефон уже не проходить чинні правила формату (`profiles/phone.ts`): користувач має виправити телефон у профілі (`PATCH /api/me`) і повторити заявку. Гість заявку подати не може; адміністратор теж (`not_a_client`).

**Контакти не приймаються з тіла.** Email береться з перевіреної ідентичності: профіль копіює його лише з Firebase ID token. Ім'я й телефон беруться з профілю. Тіло запиту строге, тож поля `email`, `name`, `phone`, `currency` чи будь-які інші дають `400 VALIDATION_FAILED`. Телефон перевірено лише за форматом. SMS-верифікації немає, і телефон ніде не називається підтвердженим (у листі: «Téléphone (non vérifié)»).

## 3. Створення: `POST /api/gift-card-requests`

Заголовок `Idempotency-Key` (8–128 символів `[A-Za-z0-9_-]`) обов'язковий.

```json
{ "amountCents": 15000, "description": "Pour l’anniversaire de ma sœur", "preferredContactChannel": "whatsapp" }
```

| Поле | Правила |
|---|---|
| `amountCents` | Ціле число центів > 0, не більше 2 147 483 647 (межа колонки `INTEGER`). Нуль, від'ємні, дробові значення, рядки й `null` → `400`. Фіксованих номіналів і бізнес-мінімуму чи максимуму немає |
| `description` | Необов'язкове. Обрізається з країв, **не більше 1000 символів**. Порожнє, з самих пробілів або `null` зберігається як `null`. Керівні символи заборонені, крім переносу рядка й табуляції |
| `preferredContactChannel` | `email`, `phone` або `whatsapp`. Це лише бажаний спосіб ручного зв'язку; інтеграції WhatsApp немає |

Валюту `EUR` визначає сервер.

**Відповідь** `201 { giftCardRequest }`:

```json
{ "id": "…", "number": 42, "status": "new", "amountCents": 15000, "currency": "EUR",
  "description": "…", "preferredContactChannel": "whatsapp", "createdAt": "…",
  "notification": { "status": "pending", "reason": null } }
```

- `number` — короткий **відображуваний** номер для людей (n° 42), той самий у листі адміністратору. Це не механізм доступу: заявку завжди адресує `id`, а доступ визначає роль.
- `notification` — стан **листа адміністратору**: `pending` / `sending` / `accepted` / `failed` / `skipped` / `interrupted`. Він окремий від `status`: помилка листа не скасовує заявку. `accepted` означає «прийнято Brevo», а не «доставлено». Причини — ті самі, що бачить клієнт для своїх листів про бронювання (`retry_scheduled`, `test_environment`, `not_sent`, …). `null` означає, що листи на сервері вимкнено.
- Контактів у відповіді клієнту немає: це його власні дані.

**Повтори** (як для бронювань):
- той самий ключ і те саме тіло → `200`, `Idempotent-Replayed: true`, та сама заявка; нової заявки й листа немає;
- той самий ключ з іншим тілом → `422 IDEMPOTENCY_KEY_REUSED`;
- ключі окремі для кожного клієнта.

**Паралельні запити** одного клієнта виконуються по черзі: транзакція бере блокування рядка його профілю (`SELECT … FOR UPDATE`), а не глобальне. Останній захист — унікальний індекс `(clientProfileId, idempotencyKey)`: якщо він спрацює, повертається заявка-переможець.

**Обмеження частоти** (погоджено 2026-11-12). Підтверджений email не захищає від частих запитів. Глобальний throttling API Gateway (2 rps, burst 10) не змінювався; спільного механізму обмеження на рівні користувача в коді не було. Тому діє мінімальне обмеження на клієнта: **не більше 5 нових заявок за рухомі 24 години**.
- Вікно — `(зараз − 24 год, зараз]`: заявка перестає рахуватися рівно через 24 год після свого `createdAt`.
- Відмова — `429 GIFT_CARD_REQUEST_LIMIT_REACHED { retryAfterSeconds }` і заголовок `Retry-After`. Значення — секунди до моменту, коли найстаріша заявка вікна з нього вийде (округлено вгору, мінімум 1).
- Повтор уже створеної заявки з тим самим `Idempotency-Key` і тілом повертає її (`200`) навіть після досягнення ліміту й ліміт не витрачає: такий повтор перевіряється до ліміту.
- Ліміт рахується з таблиці заявок у транзакції під блокуванням профілю, тому паралельні запити, зокрема на різних інстансах, його не обходять.
- Фонових процесів немає. Значення задане в `DEFAULT_GIFT_CARD_LIMITS` (`gift-card.service.ts`).

Інші відповіді: `503 GIFT_CARD_REQUEST_BUSY { retryAfterSeconds: 2 }` (рядок клієнта чи заявки або з'єднання з БД не отримано за 5 с, наприклад, коли Neon прокидається; нічого не записано, повтор з тим самим ключем безпечний). Транзакція, що перевищила свій ліміт (15 с), чи інший збій БД — `500` без деталей, як у календарі ([booking.md](booking.md), розділ 4) і стандартні `401` / `403` / `400 INVALID_JSON`.

## 4. Зберігання

Міграція `20261112120000_gift_card_requests`:

| Таблиця | Зміст |
|---|---|
| `GiftCardRequest` | `id`, `number` (serial, унікальний), `clientProfileId` → `UserProfile`, **знімок** `clientName` / `clientEmail` / `clientPhone`, `amountCents`, `currency`, `description`, `preferredContactChannel`, `status`, `idempotencyKey`, `requestFingerprint`, `createdAt`, `updatedAt` |
| `GiftCardRequestStatusChange` | Історія: `fromStatus` (`null` — подання), `toStatus`, `changedByProfileId` → `UserProfile`, `changedByRole`, `changedAt` |

- Контакти копіюються на момент подання. Пізніша зміна профілю їх не переписує (перевірено тестом).
- CHECK-обмеження БД: сума > 0, валюта `EUR`, опис 1–1000 символів або `NULL`, формат ключа ідемпотентності, перехід в історії справді змінює статус.
- Видалення заявок і редагування клієнтом не передбачено. Зв'язки з профілем — `ON DELETE RESTRICT`.
- Заявка, її перший запис історії та подія outbox для листа зберігаються **в одній транзакції**.

## 5. Адміністративний API

Лише верифікований адміністратор (`authenticate` + `requireAdmin`, як решта `/api/admin`). Клієнт і гість отримують `403 FORBIDDEN`, без токена — `401`. Клієнтських маршрутів читання заявок немає.

**`GET /api/admin/gift-card-requests`** — від нових до старих (`createdAt`, потім `number`).
- Пагінація: `page` від 1 (за замовчуванням 1), `pageSize` 1–100 (за замовчуванням 20); `total` — кількість за фільтрами на всіх сторінках.
- Фільтри: `status` і `createdFrom` / `createdTo`. Дати — локальні `YYYY-MM-DD` за Europe/Paris, межі включно; можна задати одну з них.
- Невідомі параметри й неправильні значення → `400 VALIDATION_FAILED`.

```json
{ "timeZone": "Europe/Paris", "page": 1, "pageSize": 20, "total": 1, "giftCardRequests": [AdminGiftCardRequest] }
```

**`GET /api/admin/gift-card-requests/{requestId}`** → `{ giftCardRequest: AdminGiftCardRequest }`. Невідомий або неправильний id → `404 GIFT_CARD_REQUEST_NOT_FOUND`.

`AdminGiftCardRequest` — поля клієнтської відповіді, плюс:
- `client { profileId, name, email, phone }` — знімок;
- `updatedAt`;
- `allowedStatuses` — підказка для UI;
- `history[] { fromStatus, toStatus, at, by { profileId, role, name, email } }`. У `by` — поточні ім'я й email того, хто змінив статус;
- `notification` — стан листа адміністратору: `{ status, reason, attempts, lastAttemptAt, acceptedAt }` з адмінськими причинами, як у `AdminNotification`; `null`, якщо листи вимкнено.

**`PATCH /api/admin/gift-card-requests/{requestId}/status`** `{ "status": "in_progress" }` → `{ giftCardRequest, changed }`.

| Із | Дозволено |
|---|---|
| `new` | `in_progress`, `completed`, `cancelled` |
| `in_progress` | `completed`, `cancelled` |
| `completed` | `in_progress` (виправлення помилкового завершення) |
| `cancelled` | `in_progress` (відновлення помилково закритої) |

- `completed` — ручне опрацювання завершено. Це **не** підтвердження оплати й не видача сертифіката системою.
- `cancelled` — закрити помилкову, дубльовану чи відкликану заявку; вона лишається в списку й історії.
- Повернення в `new` не передбачено. Кожне повернення в `in_progress` — звичайний запис історії з часом і адміністратором; нової заявки, події чи листа воно не створює.
- Повторне встановлення поточного статусу → `200`, `changed: false`, без нового запису в історії.
- Недозволений перехід → `409 GIFT_CARD_STATUS_TRANSITION_NOT_ALLOWED { from, to, allowed }`.
- Рядок заявки блокується на час зміни, тож паралельні зміни застосовуються по черзі.
- Листів зміна статусу не надсилає.


## 6. Лист адміністратору

- **Коли:** одразу після створення заявки. API будить відправника після транзакції, а доставка має строк «зараз»; правило 30 хвилин для бронювань сюди не переноситься. Відповідь клієнту листа не чекає.
- **Кому:** `NOTIFICATION_STUDIO_EMAIL`. На staging діє `NOTIFICATION_RECIPIENT_ALLOWLIST`: якщо адреси немає в списку, лист отримує видимий стан `skipped` / `test_environment`.
- **Зміст** — французькою, у спільному фірмовому макеті (`src/notifications/gift-card-template.ts`). Тема: «Demande de carte cadeau n° 42 : 150,00 €». У тілі:
  - номер заявки й сума в EUR;
  - ім'я, email, «Téléphone (non vérifié)»;
  - бажаний канал і опис клієнта, якщо його заповнено;
  - дата подання за Europe/Paris;
  - примітка, що онлайн-оплати й автоматичної видачі немає.
- **Безпека:**
  - усі значення, зокрема опис, екрануються в HTML і зводяться до одного рядка;
  - посилань у листі немає;
  - у технічних логах лише id, коди й статуси, без контактів і опису (перевірено тестом).
- **Надійність:**
  - помилка Brevo не скасовує й не змінює заявку: статус лишається, а `notification` показує `failed` з причиною;
  - до 3 спроб за правилами Notifications; ключ ідемпотентності Brevo — id доставки;
  - повторне подання з тим самим ключем не створює ні події, ні листа (`dedupeKey` події унікальний).
- Листа клієнту й листів про зміну статусу немає.

## 7. Конфігурація

Нових змінних немає. **`ENABLE_BOOKING_NOTIFICATIONS` тепер керує також листом про заявку на сертифікат.** Назву свідомо не змінено. Лист працює, коли прапорець `true`, з тією самою адресою студії, allowlist і ключем Brevo, що й для бронювань. Якщо прапорець вимкнено, заявки працюють, `notification` = `null`, а події чекають в outbox. Після вмикання їх надішле перший прохід, так само як накопичені листи бронювань.

## 8. Фонова активність і витрати

Нових фонових механізмів немає:
- лист іде тим самим проходом Notifications, який будить запит;
- без заявок немає ні таймерів, ні звернень до БД;
- обмеження частоти рахується в запиті;
- повтори листа — наявні: щонайбільше 3 спроби;
- зупинка — `ENABLE_BOOKING_NOTIFICATIONS=false`.

Кожна заявка дає одну транзакцію й щонайбільше 3 виклики Brevo, лише в разі збоїв.

## 9. Сумісність

- **Міграція** не лише додає дві таблиці й два enum, а й **змінює CHECK-обмеження наявних таблиць**: `OutboxEvent_type_known`, `OutboxEvent_aggregate_type` і `NotificationDelivery_event_type`. Кожне видаляється й створюється заново (DROP + ADD у транзакції міграції) у ширшій формі, що додатково дозволяє `gift_card_request.created`. Наявні рядки під них підпадають: перевірка `ADD CONSTRAINT` проходить. Даних міграція не змінює. `ALTER TABLE` бере короткий ексклюзивний lock на `OutboxEvent` і `NotificationDelivery` (таблиці малі).
- **Стара версія API на новій схемі** працює як раніше. Нових таблиць вона не знає, а подій заявок не пише.
- **Версії обробника** ([notifications.md](notifications.md), розділ 13). Розгорнутий зараз `734c672` позначив би подію заявки `invalid`, і лист пропав би. Тому до цього PR розгортається **PR #55**: його процес обробляє лише події бронювань, а подію заявки лишає незапланованою для процесу, що її знає. Перевірено тестом «versions of the sender» у `test/integration/gift-card-requests.test.ts`.
- **Порядок розгортання:**
  1. PR #55 → публікація образу → деплой без міграцій; переконатися, що активна лише ця ревізія;
  2. цей PR → міграція `20261112120000_gift_card_requests` → деплой;
  3. смоук: одна заявка тестовим клієнтом → лист на адресу з allowlist.
- **Відкат.** Після появи першої заявки — лише на ревізію PR #55 або новішу: заявки тоді недоступні (`404`), а їхні листи чекають повернення цього релізу. На `734c672` і старіші образи відкат **небезпечний**. Міграцію відкочувати не потрібно.
- **Колонка `NotificationDelivery.bookingId`** для подій заявок містить id заявки. Колонку не перейменовано: старіші версії Prisma Client її читають. Id — UUID, тож ланцюжки доставок бронювань і заявок не змішуються.
- **API бронювань не змінився:** ті самі маршрути, коди й поля. `Idempotency-Key` тепер перевіряє спільна функція з тими самими кодами.
