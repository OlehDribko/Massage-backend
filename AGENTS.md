# AGENTS.md

Інструкції для AI-помічників і розробників, які працюють у цьому репозиторії.

## Правила типізації TypeScript

Стосуються власного коду та тестів у всіх workspace (`services/*`). Архітектура — модульний моноліт ([docs/architecture.md](docs/architecture.md)).
Сторонні залежності (`node_modules`) і згенерований код (наприклад, Prisma Client) вручну не редагуються.

1. **`strict: true`** — обов'язково в кожній TypeScript-конфігурації. Строгість не послаблювати.
2. **Заборонено `any`** — явний (`: any`, `as any`, `any[]`, `Record<string, any>`, у generic-аргументах) і неявний, а також небезпечне використання значень типу `any` зі сторонніх типів.
3. **Заборонено type assertions** у будь-якій формі:
   - `value as T` та `<T>value`;
   - `as const`;
   - подвійні приведення (`as unknown as T`).
4. **Заборонено non-null assertions** (`value!`, `obj!.field`).
5. **Заборонено придушення помилок** через `// @ts-ignore`, `// @ts-nocheck`, `// @ts-expect-error`, а також вимкнення lint-правил (`eslint-disable…`) для обходу помилок.
6. **Зовнішні дані** — тіло запиту, env, відповіді API, JSON, payload токенів, повідомлення з черг — приймаються як `unknown` і перевіряються через Zod або коректне звуження типів (`typeof`, `in`, `instanceof`, type guards).
7. **Використовувати точні типи:** generics, discriminated unions, `satisfies` (замість `as`/`as const` для перевірки відповідності типу), типи, виведені зі схем (`z.infer`) та з Prisma.
8. **Не вважається type assertion:** перейменування при імпорті й експорті (`import { a as b }`, `import * as x`, `export { a as b }`).

Правила перевіряються автоматично: `npm run lint` (ESLint + typescript-eslint з type-aware правилами, конфігурація — `eslint.config.mjs`).

## Фонова активність і ресурси, що не дають засинати

Сервіс має мале навантаження: дні без запитів — нормальний стан. Neon засинає після 5 хв без активності, а постійні процеси AWS тарифікуються погодинно. Тому будь-який новий механізм, що працює без запиту користувача, додається **усвідомлено й описується в PR**:

- регулярний виклик платного ресурсу (БД, Brevo, Firebase, AWS API) — таймер, `setInterval`, цикл, cron, scheduled workflow, EventBridge/Scheduler;
- постійний worker, сервіс або задача ECS;
- механізм, що не дає ресурсу засинати: постійне з'єднання, keep-alive, прогрівання, health check, який звертається до БД чи зовнішнього API;
- повтори (власні чи SDK), зокрема накладені одні на одні.

В описі PR для кожного такого механізму:
1. **Навіщо** він потрібен і яку користь дає.
2. **Що робить у простої** (без запитів користувачів): чи звертається до БД або зовнішніх API.
3. **Частота й межі повторів:** інтервали, максимум спроб, що буває після вичерпання.
4. **Оцінка квот і витрат** за добу в простої та під очікуваним навантаженням, вплив на сон Neon.
5. **Як зупинити:** прапорець, `desired_count`, вимкнення розкладу.

Це не заборона фонового виконання, а вимога робити його видимим. Не додавайте такі механізми непомітно як допоміжну деталь реалізації. Приклад опису — [docs/notifications.md](docs/notifications.md), розділи 1 і 5: таймер лише для конкретної незавершеної роботи, без роботи — жодних звернень до БД.
